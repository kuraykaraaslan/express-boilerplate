# Observability Module

Single-facade entry point for Sentry (error + trace sink), Prometheus (metrics scrape), and OpenTelemetry (distributed tracing). Every call automatically inherits the active `tenantId` / `requestId` from the [Logger](../logger/) AsyncLocalStorage context — service code never threads observability metadata manually.

The module is **lazy** — when an env toggle is off (`SENTRY_DSN` unset, `METRICS_ENABLED=false`, `OTEL_ENABLED=false`), nothing is imported and every method is a no-op. Operators pay zero runtime cost until they opt in.

---

## Public API

| Method | Use |
|---|---|
| `ObservabilityService.init()` | Boot Sentry + Prometheus. Called from `instrumentation.ts` at Next.js startup. |
| `ObservabilityService.setTags({ tenantId?, requestId? })` | Tag the Sentry events of the open request (written to the Logger context, read by `beforeSend`). A `userId` is accepted and ignored. |
| `ObservabilityService.recordHttpRequest({ tenantId, route, method, status, latencyMs })` | Bump the request counter + latency histogram. Called by `withObservability()`. |
| `ObservabilityService.recordError(err, { tenantId?, fingerprint?, level?, extra? })` | Capture to Sentry + bump the error counter. Registered at `init()` as the sink of `normalizeError` (common), so every 5xx the API error boundary produces is captured; 4xx, Zod and SyntaxError outcomes are not. |
| `ObservabilityService.recordTenantUsage({ tenantId, metric, value })` | Per-tenant counter — feeds Grafana dashboards. Persistence still goes through `TenantUsageService`. |
| `ObservabilityService.getMetricsRegistry()` | Prom registry for the scrape endpoint. `null` when METRICS_ENABLED is off. |
| `ObservabilityService.counter / gauge / histogram(spec)` | Define a custom business metric in the shared registry; returns a handle (`inc` / `set` / `observe`). |
| `ObservabilityService.withSpan(name, fn, { op?, attributes? })` | Run `fn` inside a span (Sentry, else OpenTelemetry, else a plain call). |
| `ObservabilityService.flush(timeoutMs?)` | Wait for in-flight Sentry events to ship — call at shutdown. |

The Next.js wrapper is exported from [`server/withObservability.next.ts`](server/withObservability.next.ts):

```ts
import { withObservability } from '@kuraykaraaslan-labs/observability/server/withObservability.next';

export async function GET(request: NextRequest, { params }: { params: Promise<{ tenantId: string }> }) {
  return withObservability(request, async () => {
    // … route logic — Logger context, Sentry tags, and Prometheus metrics
    // are all set automatically.
  }, { route: '/api/tenant/[tenantId]/api/health' });
}
```

## Installation

The boilerplate ships with the facade only — install the backend SDKs when you opt in:

```bash
# Sentry
npm install @sentry/nextjs

# Prometheus
npm install prom-client

# OpenTelemetry (optional)
npm install @opentelemetry/api @opentelemetry/sdk-node @opentelemetry/auto-instrumentations-node
```

When env toggles are on but the package is missing, the facade logs a warning at boot and stays no-op — the app never crashes for a missing observability dep.

## Request metrics and the dispatcher

The tenant API dispatcher (`app/tenant/[tenantId]/api/[...slug]/route.ts`) runs every request inside `withObservability`, so `http_requests_total` and `http_request_duration_seconds` exist, the response carries `x-request-id`, and the log context holds `{ tenantId, requestId }`.

- **The route label is the registry route TEMPLATE** (`/api/store/products/[productId]`), never the concrete path, so ids and slugs never become label values. A request that never reaches a handler (no route, disabled module, unknown method) is labelled `unmatched`.
- **Order matters.** The dispatcher turns an error into its response with `normalizeError` inside the `withObservability` callback and returns it, so `http_requests_total` records the FINAL status (a thrown `AppError(404)` is a 404, not a 500). A callback that lets an error escape is counted as 500.
- `http_request_duration_seconds` has no `tenantId` label (every series costs 11 buckets); `http_requests_total` keeps it, capped at 2000 distinct values.
- The response body is never read or cloned, a streaming (SSE) response passes through; its status and duration are those of the moment its headers were returned.

## What Sentry receives

`sentry.scrub.ts` (pure functions, wired as `beforeSend`, `beforeSendTransaction` and `beforeBreadcrumb`, with `sendDefaultPii: false`) removes the user, request body, headers, cookies, query string and environment, stack-frame variables and span data, reduces the request URL and transaction name to a path template (uuid, long hex, numeric and `/tenant/<segment>` parts replaced), and scrubs uuids and emails out of messages. No user id is ever sent. The events keep the stack, the release and the `tenantId` / `requestId` tags (R-class, so a regional DSN is expected on a node).

## Rules

- **No `next/*`, no `react`.** Service-layer only.
- **Logger context is the source of truth** for tenantId/requestId. Don't thread them manually unless overriding.
- **Backends are optional.** Code that imports `ObservabilityService` works without Sentry or prom-client installed.
- **`recordError` doesn't re-throw** — caller decides whether to surface the error to the response.

## Uptime & Status (active side)

The passive facade above reports **our own** signals; the active side (phases 0–3 + bridge, 2026-08) probes the outside and publishes a status page.

**Monitors & probing.** `Monitor` rows (HTTP, TCP, PING, DNS — all four implemented) carry their own cadence (`intervalSeconds`), timeout, expected status/body and DOWN threshold. A minutely BullMQ sweep (`uptime.probe.job.ts`, see `docs/guides/cron/README.md` `uptime-probe`) probes whatever is due — one metronome for the whole fleet, never one repeatable per monitor. Every probe writes a `MonitorCheck`, bumps the daily rollup atomically, and records `uptime_check_latency_ms` / `uptime_status` in the **existing** Prometheus registry (one metric system, locked decision).

**Check types.** `runCheck` is the one place `Monitor.type` becomes behaviour; an unknown type falls back to HTTP rather than ending a fleet-wide sweep.

- **HTTP** — status / body / latency, through `safeFetch`.
- **TCP** — one handshake against `host:port`. Nothing is written or read, so a probe never shows up in the target's logs as a malformed request.
- **PING** — **not ICMP, and it says so.** A raw ICMP socket needs elevated privileges or a native module, and a container without `NET_RAW` could not send one regardless. With a port in the target it is a TCP check; without one it tries 443 then 80, and the error names the ladder so an operator sees what was attempted instead of guessing at "ping failed".
- **DNS** — `A@host`, `TXT@host`, `CNAME@`, `MX@`, `AAAA@`, or a bare host (defaults to A). NXDOMAIN and an empty answer are both DOWN; a name that resolves to nothing is not up. `expectedBodyContains` doubles as the expected VALUE — which catches the failure "does it resolve" cannot: a hijacked or fat-fingered SPF record still resolves while mail silently breaks. It is reused rather than given its own column, because one nullable column per check type is how a monitor table becomes a union of four.

- **TLS** — one handshake through the same address guard; the certificate is judged for expiry, hostname, chain trust and not-yet-valid. `certWarnDays` (default 30) makes the sample DEGRADED, `certCriticalDays` (default 7) makes it DOWN. An HTTPS monitor with `certWarnDays` set gets the same check on top of its HTTP verdict and can only get worse for it.
- **DOMAIN** — registration expiry from RDAP (IANA bootstrap, `safeFetch`, cached for hours). A TLD without RDAP, a registry that hides the date, or a registry that is down is an **inconclusive** sample: stored with its reason, `UNKNOWN`, and ignored by the debounce, the rollup and incidents. Not knowing is not "up", and it is not an outage either.
- **HEARTBEAT** — the job calls `GET|POST /api/public/heartbeat/<token>` (optionally `/start` for a duration and `/fail` for an immediate failure); silence is the failure. The token is a credential: only its SHA-256 is stored, it is returned once on create / rotate / clone, and anything that does not match answers the same 404. A ping records its own UP sample; the minutely sweep only records a sample when the job went quiet, so the debounce and incident machinery run unchanged. A brand-new monitor is measured from its creation: it gets one full period (plus `heartbeatGraceSeconds`) before it can fail.
- **STEPS** — up to 10 requests in sequence, a later step using a value extracted from an earlier one (`{{token}}`) or a stored secret (`{{secret.NAME}}`). The grammar is closed (no branching), every step goes through `safeFetch`, the whole run shares one time budget, secrets are stored encrypted and never returned (the API lists their names), and a stored failure reason never contains a secret value.

**Assertions.** `assertions` holds typed rules (status set, header, body contains / matches, JSONPath equals / exists / contains / gt / lt / between, latency budget, size). `expectedStatus` and `expectedBodyContains` keep working and are read as rules of their own. A failed rule is DOWN, except a latency budget, which is DEGRADED by default. Failure reasons name the rule and the path and never echo a response value. JSONPath is the `$.a.b[0]` subset; regular expressions are length-capped, refused when they have a nested quantifier or back-reference, and applied to a capped prefix of the body (a mitigation, not a proof: a linear-time engine is the real fix).

**Operating many monitors.** Groups and tags, pause-until (`pausedUntil`, expires by itself), a per-monitor maintenance window (`maintenanceUntil`: samples are marked `duringMaintenance` and open no incident), bulk pause / resume / delete / maintenance (`POST /api/monitors/bulk`, 200 at a time, tenant-filtered), clone, and CSV / YAML / JSON import (`POST /api/monitors/import`, dry run by default, all-or-nothing). An optional latency baseline (`latencyBaselineFactor`) turns a healthy sample far slower than the monitor's own recent median into DEGRADED.

**Schema.** `roltek-monitor-1` (`schema/roltek-monitor-1.schema.json`) is generated from the same DTO the create route validates with (`npm run gen:monitor-schema`; a test fails when the committed file is stale).

**SSRF guard.** A probe target is user-defined, so every request goes through the shared guard in `common`: HTTP through `safeFetch` (resolve, pin the connection to the resolved IP, block private/internal ranges, re-check every redirect hop) and TCP/PING through `createValidatingLookup`, which is that same pinning shaped as a `net.connect` lookup. There is deliberately no probe-local HTTP client and no second address guard — a second one would drift, and drift in an SSRF guard looks like a working uptime monitor.

**Debounce & incidents.** `applyOutcome` is a pure state machine: DOWN is declared only after `consecutiveFailThreshold` consecutive failures (default 3), recovery after consecutive successes — flapping never pages. A debounced DOWN transition auto-opens an `Incident` (at most one OPEN per monitor, enforced by a partial unique index) **unless an active maintenance window says the outage is expected** (read from `tenant` over the bridge; the check fails closed to "not in maintenance" so a lost alarm never happens silently). Auto incidents open **private**; flipping `isPublic` is a separate, narrow permission (`observability.status.publish`) because it is an outward-facing act.

**Components & the public page.** `StatusComponent` rows map monitors many-to-many and derive their status worst-of (operator-set MAINTENANCE sticks until handed back). The public `/status` page + `GET /api/public/status` serialize through ONE allowlist builder (`status.public.service.ts`) — fields are copied one by one, so a monitor `target`, header or internal reason can never leak through a forgotten omit.

**Branding.** The page carries the tenant's own chrome — name, logo, primary colour — served in the same response rather than fetched separately, because a second client fetch is a second thing that can fail on exactly the day it must not. It is a four-field allowlist (`status.branding.ts`) and the omissions are the design:

- `customCss` / `customJs` are **never** included. Tenant-authored script on the status page means the page goes down with whatever broke — the page whose entire job is to still be standing — and it is an anonymous, unauthenticated surface, the worst place to evaluate strings a tenant admin typed.
- `brandPrimaryColor` colours the **header only**, never a status indicator. The greens and reds are semantic; repainting an outage in a brand colour makes a broken service look fine.
- Everything else is omitted because no consumer exists yet. A field is added when one does.

`tenant_branding` being absent or switched off for the tenant degrades to the plain page (dynamic import, `dependencies.optional`, EXT-14), the same rule the maintenance bridge follows. `statusPageEnabled` defaults **false**; disabled is indistinguishable from nonexistent (404). Subscribers are double-opt-in and get incident + maintenance mail (tokens are their credentials — never serialized to admins); that mail leaves through `NotificationService.notify()`, never the mail queue (PLAT-01) — the recipient is address-only, which the dispatcher supports since `NotificationRecipient.userId` became optional.

> **Gap closed (phase 15, 2026-10-18):** status mail used to be noted as bypassing `contact.SuppressionService`. The gate had meanwhile moved into `notification.policy` as the `notification:suppression` extension point (`contact` contributes its list of unsubscribes, hard bounces and complaints), so every status mail, which leaves through `NotificationService.notify()` as an address-only, `NORMAL` urgency, mail-channel notification, is already judged before any channel runs, without `observability → contact`. Phase 15 pins that call shape with tests on both sides (this module asserts the shape, `notification` asserts the decision) and never uses `CRITICAL` or a marketing category for status mail: a hard bounce or a complaint stops an outage notice, a marketing-only unsubscribe does not. Subscriptions are double-opt-in with a per-mail unsubscribe link. Live updates ride the shared websocket gateway (`/status` namespace, payload-free "changed" event); without the gateway the page polls.

**Maintenance is not downtime.** Two places say so, and neither writes anything back to `tenant`, which stays the single source of a window.

- *The page.* A SYSTEM or TENANT window repaints every available component as MAINTENANCE at **read time** (`projectMaintenance`). Persisting it would need a reliable un-write when the window closes, would fight the operator's own sticky MAINTENANCE, and would put a second copy of the window's truth in this module. A component the probes call an outage keeps saying outage — planned work explains an expected failure and must never hide an unexpected one. ROUTE windows are partial by definition and there is no window→component mapping to narrow them with, so they repaint nothing and show in the maintenance block instead.
- *The number.* `observabilityExcludeMaintenanceFromUptime` (default **on**) keeps samples taken during a window out of the daily rollup, so the uptime percentage describes UNPLANNED availability — the only kind a status-page reader is asking about, and the reading that does not punish a tenant for announcing their work. The raw `MonitorCheck` is still written and carries `duringMaintenance`, so nothing is hidden. Exclusion happens at write time: per-day counters cannot have a two-hour window subtracted from them once raw checks are pruned, and history should not rewrite itself when a setting is toggled. The bridge read fails **closed** — a hiccup counts the sample and raises the alarm rather than silently excusing an outage.

## Alert pipeline (phase 11)

A **signal** becomes an **alert**; alerts are deduplicated, grouped, muted, inhibited and routed; an **incident** is the human response unit that may answer for many alerts. They are different records on purpose: before this layer a probe flap *was* an incident, which could neither group, silence nor route.

- **Alert** (`alerts`): one non-resolved row per `(tenant, fingerprint)` (partial unique index), so a re-fire updates the row and bumps `count` and an alert storm is a counter, not a table explosion. Never deleted: it is FIRING, SUPPRESSED (with the reason: `maintenance`, `silence:<id>`, `inhibited:<entity>`, `dropped`) or RESOLVED. A monitor's alert has the monitor as identity (`monitor:<id>`), so renaming it while it is down cannot orphan the recovery.
- **Sources.** Monitor outages and recoveries, missing process kinds (ROOT tenant), outside systems through **ingest keys**, alerts raised by hand, and modules through the `observability:alert-source` extension point (below).
- **Ingest** (`POST /api/public/alerts/ingest/<key>`, no session). A key is a credential: only its SHA-256 is stored, it is shown once, and it fixes the tenant, the parser (generic JSON, Prometheus Alertmanager webhook v4, Grafana), the highest severity it may send and its default labels. The sender controls labels and annotations only; severity is clamped to the key's ceiling; the `entity` and `monitorId` labels are **reserved** (a sender that could set them could mute another system's alerts by claiming to be its parent); the body and the alert count per request are capped; every kind of miss answers the same 404.
- **Decision** (`alert.decision.ts`, one pure function used by ingest and by the routing simulator, so "where would this go?" cannot disagree with "where did it go?"): suppression first (planned maintenance, then a silence, then the dependency graph, then a `drop` route), then the first matching route (or the built-in default), its grouping and its targets.
- **Routing rules.** Ordered label matchers (`=`, `!=`, `=~`, `!~`; regular expressions anchored and guarded like the monitor assertions) with `groupBy`, `groupWait`, `groupInterval`, targets, an optional incident override, and `continue`. Targets: `notify` (users or addresses through `NotificationService`), `webhook` (the `alert.firing` / `alert.resolved` events, which also reach automation flows through `webhook:event_sink`), `on_call` (below), `drop`.
- **Grouping.** `groupWait` holds the first alert of a group so siblings can join; `groupInterval` spaces announcements of the same group. Both are a `dispatchAfter` time on the alert, announced by a minutely sweep (`observability-alert-dispatch`, serverless twin `POST /api/cron/alert-dispatch`), so nothing lives in memory and a restart loses nothing. A group is announced **at least once**: claiming sets a short lease, the side effects run, then the alerts are marked announced; a crash in between lets the lease lapse and the group is announced again (a repeated message is recoverable, a lost alert is not), and the notification call carries an idempotency key.
- **Silences.** Time-bound (at most 30 days), a reason is required, at least one matcher. A silence mutes the *announcement*; the alert is still stored, names the silence, and comes back by itself when the silence ends.
- **Dependency graph.** `child depends on parent` over opaque entity keys (`component:<id>`, `process:<kind>`, `monitor:<id>`, `ext:<module>:<key>`); a loop is refused when written. While any ancestor has a firing alert, the child's alerts are SUPPRESSED (`inhibited:<entity>`) and return when the ancestor recovers. Alertmanager cannot do this because it cannot know the API depends on the database; the status components and process kinds are that knowledge.
- **Incident policy.** Per severity (`observabilityIncidentOn<Severity>` settings), overridable per route: `auto` opens one incident per group, `never` only records. The default reproduces what the platform did before the alert layer: a debounced monitor outage opens a private auto incident, INFO and WARNING only record. When the last alert of an auto-opened incident recovers the incident closes itself; a manual incident is never closed by the machine.
- **A target that cannot deliver is reported, not dropped:** it raises a WARNING alert (`AlertTargetUnavailable`, one per target type, cleared when that target works again).
- **`observability:alert-source`.** A module reports what is firing now through `{ listFiring(tenantId) }`; the pipeline raises what is listed and resolves what that module raised before and no longer lists. A provider that throws leaves its alerts untouched (failing to look is not recovery). The pipeline assigns the entity (`ext:<module>:<key>`), so a contribution cannot claim to be another system's parent.
- **On-call.** The `on_call` target pages through the module's real contract (`OnCallService.page`, reached with `ifActive`, never a static import): the policy, the alert group as the `dedupKey` (so a group is ONE page), `source: observability:alert`, a pager-level severity (CRITICAL and MAJOR page as CRITICAL, MINOR and WARNING as WARNING, INFO as INFO) and the group payload as metadata. When the last open alert of the group recovers, `resolveByDedupKey` resolves the page. A module that is absent, switched off, or a policy it refuses is a visible `AlertTargetUnavailable` alert, never a silent drop. In the other direction observability contributes to `on_call:health`: a failed paging self-test becomes a CRITICAL `OnCallSelfTestFailed` alert (one alert, repeats are a counter), recorded outside the paging path, and a passing one resolves it.
- **Metrics:** `alerts_ingested_total`, `alerts_suppressed_total`, `alert_groups_dispatched_total`, `alert_target_failures_total`, `alert_ingest_rejected_total` (every call is wrapped: telemetry must not stop an alert).
- **Permissions:** `observability.alerts.read` and `observability.alerts.manage`, both ADMIN-floored. (The older `observability.monitors.read` has a known invalid MEMBER floor, S11; the new permissions deliberately do not inherit it.)
- **Screen:** `/admin/alerts` (alerts with acknowledge / resolve, routing rules with a simulator, silences, ingest keys, dependencies).

## SLOs and burn-rate alerts (phase 13)

An SLO says how reliable a service must be (an objective over a rolling 7, 28, 30 or 90 days) and turns the gap into an **error budget**: 99.9 % leaves 0.1 % that may go wrong, and the screen shows how much of it is left, how fast it is being spent, and when it would run out at that pace.

- **What the events are.** `MONITOR_AVAILABILITY` (a monitor sample that was up or degraded is good, down is bad, an inconclusive sample is not an event), `MONITOR_LATENCY` (good means up and answered within a threshold), `METRIC_RATIO` (two metric queries, good and total; **platform workspace only**: a tenant never submits raw metric queries, they would read other tenants' series). An SLO may name monitors, or a status component and use that component's monitors.
- **No data is not 100 %.** An unmeasured window is `NO_DATA`; a metric SLO stays `NO_DATA` until a backend is wired (`setMetricSliSource`, provided over the telemetry port in phase 17), so a missing backend can never read as "all good".
- **Where the numbers come from.** The whole window reads the **daily rollup**, which survives raw-check retention; the short alert windows read raw checks through aggregate SQL (a 3-day window over ten monitors is tens of thousands of rows and is never pulled into memory). Maintenance is left out exactly as the rollup left it out (`observabilityExcludeMaintenanceFromUptime`), so the SLO and the uptime figure cannot disagree. Latency is not in the rollup, so a latency SLO only looks back as far as raw retention, and the report says so (`limitedByRetention`).
- **Burn-rate alerts** use the multiwindow, multi-burn-rate method of the Google SRE Workbook (chapter 5, table 5-8, verified against the page before it was encoded): page at 14.4x over 1 h (2 % of the budget), page at 6x over 6 h (5 %), ticket at 1x over 3 d (10 %); each tier needs its short window (1/12 of the long one) to burn too, so an alert ends about five minutes after the errors do. The thresholds are derived from "share of the budget consumed over the long window", which reproduces 14.4 / 6 / 1 at 30 days exactly and scales correctly for 7, 28 and 90. A fast-tier alert is CRITICAL, medium is MAJOR, the ticket is WARNING, each is one alert per SLO and tier (`source: slo`), carries the SLO's component as an entity (so the dependency graph can mute it), and resolves when the burn stops.
- **A deviation, on purpose:** the short window must contain at least **two bad events**. With probes a minute apart a 5-minute window holds five samples, so one failed probe is a 20 % error rate, over any burn threshold; without the guard a single blip would page. Request-rate SLIs have thousands of events and never notice it.
- **Budget events.** `slo.budget_low` and `slo.budget_exhausted` webhook events (they also reach automation flows, for example to slow releases) fire when the budget gets WORSE than where it was last seen, not every minute and not on recovery. The last state lives on the SLO row.
- **OpenSLO v1** import and export (`GET|POST /api/slos/openslo`): one rolling day window, `Occurrences`, one objective, a ratio indicator whose source is `roltek.monitor` (monitors) or `prometheus` (queries). Anything else is refused with a reason and never guessed at: time-sliced budgeting, calendar windows, several objectives, threshold indicators, other source types. Imports are validated by the same DTO as a hand-made SLO and all-or-nothing; YAML aliases are bounded.
- **Screen and widget:** `/admin/slos` (budget cards, detail with the three tiers and the daily series, create, OpenSLO export / import) and a dashboard widget of the SLOs with the least budget left. Permissions `observability.slos.read` / `.manage`, both ADMIN-floored.
- The existing `GET /api/slo` (this process's request percentiles since boot, ROOT only) is a different thing and stays.
- **Burn series for a chart (13.5).** `GET /api/slos/{sloId}/burn?points=N` (`observability.slos.read`, rate limited, `Cache-Control: no-store`) returns the burn rate and the error budget left over the SLO window plus, per tier, the current short and long window burn. `points` is 2 to 200 (default 120; outside that is a 400). The arithmetic is the same pure module the tier evaluation uses (`slo.budget.ts`), and the `current` block is the report of the same evaluator, so a number on the chart is the number the alert saw (a test pins the newest hourly point to the fast tier's one-hour window and the last point's budget to the report). **Resolution is stated per point** (`resolution`: `day` from the daily rollup, which survives raw retention; `hour` from raw checks for the newest hours, never older than the retention window; `merged` when days or hours had to be folded to honour `points`; `source`: `rollup` or `raw`). A point with no events has `burn: null` and the budget is carried across it, never 0 and never 100 %; before the first event the budget is `null`. A partial window and a changed objective behave as the budget math defines (the current objective applies to the whole window: history is not versioned). Latency SLOs have no rollup, so their series is raw-only and says it is limited by retention; metric SLOs (ROOT only) have no history, so their series is empty. The chart is the vendored kui-react `BurnChart` in the SLO detail (budget left in percent, burn rate, the SLO's own tiers as thresholds, the projection to zero, the window end); a bucket with no events or no budget yet contributes no point, so the chart joins its neighbours and never draws a zero. The daily SLI list is a `DayBarChart` against the objective.
- **SLA report export (13.5).** `GET /api/status-pages/{pageId}/sla-report` (`observability.status.read`; the components that page shows, `default` is the default page; `objective=99.9` judges every row) and `GET /api/slos/{sloId}/sla-report` (`observability.slos.read`; availability SLOs only, the SLO's objective is the target), both with `from` / `to` (UTC dates, inclusive; at most 92 days, starting at most 366 days back), `format=json|csv|pdf`. Per row: total minutes, **excluded maintenance minutes**, **unknown minutes**, downtime minutes, uptime %, incident count, outages, longest outage and objective met. **Maintenance semantics are the status page's:** the published `uptimePercent` is read from the same daily rollup the status page and the SLOs read, in which a sample taken during planned maintenance was never counted when the tenant keeps maintenance out of uptime (`observabilityExcludeMaintenanceFromUptime`, decided when the sample was written); the minute figures come from raw checks, where the same flag marks maintenance coverage: it is the UNION of the windows (two overlapping windows are not subtracted twice), an outage inside it is not downtime, an outage partly inside it counts only its outside part, and with the setting off the flag is ignored everywhere. Time nobody measured (no probe, a gap longer than twice the probe interval, only inconclusive probes) is **unknown**, reported separately and never counted as up; no samples at all is `null` where the status page shows 100. Several monitors or locations are combined per instant (down if any is down; maintenance only when every voter with data is in it). Minute figures are `null` (with the reason) for a period older than raw retention while the published figure remains. The arithmetic is a pure module (`sla.report.ts`) tested against hand-computed fixtures, and a service test checks that the report's percentage equals `StatusUptimeService.uptimeWindows` on the same rollup. **CSV** is RFC 4180 with formula neutralisation (a cell starting `= + - @` tab or CR gets a leading apostrophe) and control characters removed; **PDF** is rendered with jsPDF (the repository's one PDF engine, as the invoice renderer uses), Latin-1 text only, no links, scripts or actions, and the file name is `sla-report-<ascii slug>-<from>_<to>.<ext>`. At most 300 monitors and 1.5 million raw rows per report (a 422 asks for a shorter period), at most 2 reports at a time per tenant (a 429), and every export is audit-logged (`observability.sla_report.exported`: ids, period, format and row count, never content).
- **Platform SLO rules for Prometheus (13.4).** `infra/prometheus/slo-rules.yml` is generated (`npm run gen:alert-rules`, checked by `npm run check:alert-rules` and a drift test) from `server/slo-rules.ts` for the platform's own request SLOs, using only metrics that exist in `metrics.ts` (`http_requests_total{status}`, `http_request_duration_seconds_{bucket,count}`). Per SLO it records the error ratio over every window the tiers use and the error budget left, and alerts per tier (`SloBurn`, labels `slo`, `tier`, `action`). The tiers, thresholds and the two-bad-events guard are imported from `slo.budget.ts`, so the YAML cannot drift from the in-product evaluation (a test parses the YAML and compares). `promtool check rules` and `promtool test rules` (`infra/prometheus/tests/slo-rules.test.yml`, six scenarios mirrored in a vitest against `evaluateTier`) run with `npm run test:prom-rules`, which skips when no `promtool` is found (`PROMTOOL=/path`, or `--require` to fail). `METRIC_RATIO` SLOs of the product stay ROOT-only and read `NO_DATA` until a backend is wired.

## Incident management (phase 14)

An incident is the human response unit: the alert pipeline opens one per alert group (or a person declares one), and the response workflow lives on it.

- **Timeline.** `incident_events` is append-only with a fixed set of event types (declared, alert linked, acknowledged, mitigated, resolved, severity changed, published, public update, role assigned, task added, note added, post-mortem). It is a state-machine history, **not** a polymorphic activity table (audit §3.2): no `relatedType` reach, small bounded detail, and free text lives in `comments`. Recording is best-effort: it can never be the reason the thing that happened fails.
- **Lifecycle.** `acknowledgedAt/By` (the first acknowledgement stands: who saw it first is a fact), `mitigatedAt` (impact stopped, still open), `declaredBy`. A manual incident is declared with `POST /api/incidents`; the machine closes only the incidents it opened itself.
- **Roles.** Commander, comms lead, responder, observer; one role per person, at most one commander (partial unique index). Handing the command to someone else moves the previous commander to responder in the same step and says so on the timeline.
- **Notes and follow-ups** are `comments` (subject `incident`) and `tasks` (related type `INCIDENT`) records, optional modules reached on demand: without them writes answer a clear 409 and reads are empty.
- **What changed.** The `observability:change-event` extension point (`{ listChanges(tenantId, from, to) }`) plus the audit log (module, flag, setting, release actions) answer "what changed in the hour before this started, and during it". A provider that throws is skipped.
- **Post-mortems.** A draft built from the incident's own timeline (blameless: lines say what happened, never who), a review step with a reviewer who is not the author and a root cause written, then publication, which takes the narrow `observability.status.publish` permission and needs a resolved incident. A published write-up is locked; withdraw it to edit.
- **Post-mortem review and publication through `approval` and `document` (respond track).** The `incident_postmortems` row stays the content source. With `approval` in use, sending a post-mortem for review creates an approval item of entity type `incident_postmortem` (the two pre-checks, reviewer is not the author and the root cause is written, run first); the decision returns through a handler and a decision guard registered at boot (`incident.postmortem.integration.ts`, like `on_call.approval.ts`): APPROVED leaves the row in review with `reviewOutcome = APPROVED`, REJECTED sends it back to a draft, and the author deciding their own write-up is never a review. Without `approval` the original built-in review applies (`reviewMode = BUILTIN`). Publication (still `observability.status.publish`) renders the write-up as Markdown and files it as a NEW VERSION of a `document` record (type `INCIDENT_POSTMORTEM`, INTERNAL, CONFIDENTIAL for a private incident); the document id is kept on the row and a republication after a withdrawal adds the next version, never editing an earlier one. A document that cannot be filed leaves the post-mortem unpublished. The post-mortem never appears on the status page. Both modules are optional: neither is a hard import.
- **Slack and Microsoft Teams posts (respond track, migration 066).** Per-tenant destinations (`/api/chat-destinations`, `.../[destinationId]`, `.../[destinationId]/test`; screen: "Slack and Teams destinations" on `/admin/incidents`): a kind, a label, an incoming-webhook URL, an audience, optional event and severity filters, on/off. Events: `incident.created`, `.updated`, `.acknowledged`, `.mitigated`, `.resolved`, `.postmortem_published`. No installed module posts to chat, and `webhook` delivers signed envelopes, so `chat.sender.ts` is a small sender that keeps `webhook`'s SSRF-pinned `safeFetch` (no redirect, short timeout) and adds retry with backoff. The webhook URL IS the credential: only the vendors' own hosts and https are accepted (`chat.destination.ts`: no userinfo, port, fragment, lookalike host or IP literal), it is stored AES-256-GCM encrypted, shown as its host only, never in a response, audit row, log line or export, and a platform without the encryption key refuses to store one. Messages are drawn by pure formatters (`chat.format.ts`: Slack Block Kit with the `&amp; &lt; &gt;` rules, Teams Adaptive Card) after every person-typed string is defanged (no `<!channel>`, `<@U123>` or link syntax survives; unfurling is off). A destination flagged PUBLIC receives only created / updated / resolved of an incident that is public, with its public words and the status page link; a private incident, an acknowledgement, a mitigation, the reason, the console link and a post-mortem never reach it. Reads need `observability.incidents.read`; writes and the test message need `observability.chat.manage`; the test message has the strictest rate bucket and a 10 second per-destination cool-down. A destination that answers 403, 404 or 410, or fails ten times in a row, is switched off; one dead destination never delays another or the incident itself.
- **Public update wording.** Defaults per status in code; a tenant overrides per locale; an unknown locale falls back to the English override, then the default. Placeholders are a closed set (`{{title}}`, `{{components}}`, `{{severity}}`) replaced as plain text.
- **Events.** `incident.opened`, `incident.updated` (acknowledged, mitigated, edited, public update) and `incident.resolved` webhook events, which also reach automation flows.
- **Analytics** (`GET /api/incident-analytics?days=`): time to acknowledge and to resolve (mean and median), time between incidents, counts by severity, component and day, alerts per incident, share opened automatically. Nothing measured is null, never zero; a negative interval is ignored.
- **Screen:** `/admin/incidents` (numbers, list, declare, and a detail view with the actions, timeline, people, follow-ups, notes, changes and post-mortem). Permissions: `observability.incidents.read` (ADMIN) for the new reads, `.manage` for the writes, `observability.status.publish` for publishing a post-mortem.

## Monitoring-as-code, API and importers (phase 21)

Everything an operator configures can live in a repository: one document, one CLI, one REST surface, and converters from the tools people are leaving.

- **One document, `roltek-observability-1`** (`server/config/config.dto.ts`, JSON Schema in `schema/roltek-observability-1.schema.json`). Monitors, status components, SLOs, silence **templates** (a live silence is state, not code), alert ingest integrations (**metadata only**: a key is never in a file), alert routes, dependencies and incident update templates. Every resource has a stable `key`; references name keys, never ids. It is assembled from the DTOs the REST routes validate with, so the file format, the API and the schema are one description; `npm run gen:observability-schema` writes the JSON Schema and the OpenAPI document, `npm run check:observability-schema` and a drift test fail when they are stale. Rules that span entries (unique keys, resolvable references, loop-free dependencies) are one function (`checkDocument`) shared by the CLI and the server. On-call schedules and policies are **not** in this document: they belong to `on_call`, which has its own configuration document with the same plan, apply and CLI (`roltek-on-call-1`, see the `on_call` module README).
- **Identity and ownership.** A resource applied from code carries `managedBy = 'code'` and `sourceKey = 'code:<key>'` (migration `020`; dependencies and update templates are identified by what they are and only get the mark). Code-managed rows are **read-only everywhere else**: the services refuse an edit or delete that is not an apply (409), the console badges them and hides edit and delete. What stays open to hand is state, not definition: a component's MAINTENANCE status, a monitor's pause-until and maintenance window, rotating a credential. **Detach** (`POST /api/observability/config/detach`, the Configuration screen) hands a row to the console and releases its key.
- **Plan, apply, drift.** `POST /api/observability/config/plan` compares the document with the live rows field by field and answers create / update / adopt / delete / orphan / noop; header values and step secrets are compared server-side and reported by **name only**. `apply` is idempotent (the second run plans nothing), validates and plans everything before the first write, runs under a per-workspace lock, accepts the plan hash it was shown, and stops at the first failure naming where (the services open their own transactions, so a stopped run is finished by running it again). Nothing is deleted without `prune`, and only code-managed rows are ever deleted; `adopt` takes over console resources of the same name instead of duplicating them (an export of a console-built workspace applies cleanly with `adopt`). A created HEARTBEAT monitor or integration issues a credential: returned once to the caller of that apply, never stored in the clear.
- **Two lanes to the config endpoints, never mixed** (`server/config/config.auth.ts`): a request with an `Authorization` header is judged only as an `api_key` holding `observability_config:read` (export, plan, list, OpenAPI) or `observability_config:write` (apply, detach), pinned to the URL tenant; otherwise a session must hold the console permission of **every kind the request names** (manage to apply, read to plan). The coarse `read` / `write` verbs satisfy neither scope; `admin` and the `observability_config:*` wildcard do. The scopes are listed in `ServiceScopeEnum` (`api_key.enums.ts`): a scope outside that enum cannot pass `SafeApiKeySchema`, so a key holding it could not verify at all. Reading monitors and components asks for `observability.monitors.manage`, not `.read`, because the read permission has the invalid MEMBER floor (S11): stricter than the console, never looser.
- **Routes:** `GET /api/observability/config` (export; `scope=managed|all`, `kinds`, `format=yaml|json`), `POST .../config/plan`, `POST .../config/apply`, `GET .../config/managed`, `POST .../config/detach`, `GET /api/observability/openapi`, `GET|POST /api/alert-silence-templates` (list; start a template, which creates a normal silence), and `GET /api/incidents/[incidentId]` (added for REST completeness).
- **Hostile input.** A body is capped (declared length first, then while streaming), a document is at most 1 MB and 60 000 values, YAML is the core schema with one document and at most 10 alias expansions, any `__proto__` / `constructor` / `prototype` key is refused at any depth, unknown fields are errors, and a validation message names the expectation and never the received value.
- **The CLI** (`modules/observability/scripts/cli`, `npm run observability -- <command>`): `init`, `validate` (offline), `diff` (exit **2** on drift, for CI), `apply` (`--dry-run`, `--prune`, `--adopt`, `--kinds`, `--expect-plan <hash>`, `--credentials-out <file>`), `export`, `import --from <tool>`. The api key is `OBS_API_KEY` or `--api-key-file`, **never a flag** (a flag that looks like a credential, or any `--flag=value`, is refused without echoing the value); the server must be https (loopback excepted). Secret values in a file are references, `{ fromEnv: OBS_... }` (only `OBS_`-prefixed variables are readable, so a pull request cannot read the CI's other secrets) or `{ fromFile }` (only under `--secrets-dir`). Every byte the CLI prints is scrubbed of every secret it has held, `--verbose` prints method, path and status only, and credentials the server issues go to a file with mode 0600, never the terminal. A test greps the output of every command, flag and failure for planted secrets.
- **Importers** (`server/config/importers`), each a converter to the document with a report **before** anything is written and all-or-nothing: Uptime Kuma 1.x backup, UptimeRobot (getMonitors JSON, bulk CSV), Atlassian Statuspage components (subscribers are never copied: they re-confirm through double opt-in), Prometheus rule files (alerting rules become **disabled** routes plus an Alertmanager integration; PromQL, `for` and recording rules are refused with the reason). Header values, passwords and push tokens are never copied: environment references are written and listed. Opsgenie and Grafana OnCall schedules and escalations convert to a `roltek-on-call-1` document (`on_call/server/on_call.import.ts`) applied by `POST /api/on-call/import`. What each cannot map, and what was verified against the source tool's documentation and what was not, is in the phase file.
- **Events** added for the rest of the lifecycle: `alert.acknowledged`, `incident.postmortem_published`, `status.component_changed`, `observability.config_applied` (counts and kinds, never contents), alongside the existing alert, SLO and incident events. **CloudEvents** is an OPTIONAL envelope per webhook subscription (`format: cloudevents`, see the `webhook` module README); the default payloads are unchanged.
- **Versioning policy.** The API is versioned by contract, not by URL: the OpenAPI document carries a major version (`x-api-version`), and the document a file declares (`schema: roltek-observability-1`) is the contract it was written against. Additive changes (a route, an optional field) keep the version; a breaking change ships as a new document and schema id (`-2`), and the old one keeps working for at least two minor releases of the platform.
- **Authorization parity.** A session apply needs exactly what the same action in the console needs, for every kind it names, so a person who may manage alerts but not SLOs cannot apply a file with SLOs in it; a key stands for an administrator who chose to hand over the whole set of `.manage` permissions and is therefore its own scope pair that `write` does not imply.
- **Terraform / OpenTofu provider** (ADR-0011, D-OBS-10): `tools/terraform-provider-roltek-observability/` (Go, terraform-plugin-framework), GENERATED from the published contract: `npm run gen:terraform-provider` reads `schema/roltek-observability-1.schema.json` and the OpenAPI document and writes the resource schemas, CRUD wiring tables and docs; `npm run check:terraform-provider` (and a vitest) fail when the committed generated files are stale. Resources `roltek_observability_monitor`, `_status_component`, `_slo`, `_alert_route`, `_alert_integration` (the credential is returned once, kept as a sensitive attribute), `_alert_dependency`, `_silence_template`, `_incident_update_template`, and the data source `roltek_observability_config`; authenticated with an `observability_config:write` key. Proven live against the real handlers over a real Postgres with Terraform 1.16.6 and OpenTofu 1.13.1 (plan, apply, no-drift plan, update in place, drift repair, import, adopt, destroy of one resource without touching its siblings, bad key, read-only key). Needs two small server features it added to the document: `pruneKeys` (delete exactly the named code-managed keys) and an optional explicit route `position`. Not published anywhere; see its README and the ADR for what was not exercised.
- **Operational routes for machine keys** (work order 2): a CI key can acknowledge an alert (`POST /api/alerts/{id}/ack`), declare an incident (`POST /api/incidents`), start a silence from a template (`POST /api/alert-silence-templates`) and add an incident note (`POST /api/incidents/{id}/notes`) with four narrowly scoped keys: `observability_ops:ack`, `:incident`, `:silence`, `:note` (registered in `ServiceScopeEnum`). Same two lanes as the configuration routes but a stricter credential rule (`server/ops/ops.auth.ts`): the scopes are matched EXACTLY against the key's own list, so `admin`, `*`, `write`, `observability_config:*`, the MCP scopes and the other ops scopes grant none of them; the key's tenant is the call's tenant and a mismatch is the same 401 as an unknown key; every refusal before authentication is that same 401; 30 calls a minute per key (429); every call past authentication is audited through `audit_log` as actor `API_KEY` with the action, outcome (`ok` or `error_<status>`) and target id, never the body. A machine-declared incident opens private, with no declaring user, and its reason ends with `[declared by API key abcd1234]`; a machine note is written under the name `API key abcd1234`. The session lane is exactly as before.
- **API docs.** The OpenAPI document is contributed to `api_doc` through its new extension point `api_doc:openapi-source` (`server/observability.openapi-source.ts`) and appears in the API docs selector; `GET /api/observability/openapi` serves the same document.
- **Importers.** Source formats were checked against vendor documentation and source on 2026-10-18; the evidence, with URLs, is in `docs/phases/09-observability/21-importer-verification.md` (UptimeRobot codes and keyword semantics, Uptime Kuma 2.x, Statuspage groups, Opsgenie escalations and cumulative rotations, Grafana OnCall units).
- **On-call as code.** `roltek-on-call-1` is also a configuration document for schedules and escalation policies, applied like this one (export, plan, apply, detach, `--target on-call` in this CLI); see the `on_call` module README. The Opsgenie and Grafana OnCall importers produce the same document.

### Live lane
`OBS_LIVE=1` switches on the `*.live.test.ts` files, which run the REAL route handlers (`app/tenant/[tenantId]/api/[...slug]/route.ts`, served by `scripts/live/route-server.ts`) over a real Postgres (a scratch database filled by `npx tsx modules/db/scripts/db-deploy.ts`; point `OBS_LIVE_DATABASE_URL` at it, default `postgresql://postgres:postgres@localhost:5432/obs_aicode_live`), real Redis and real api keys (`scripts/live/live-fixture.ts` mints keys straight into the table: the create route's plan gate is a billing rule, not under test). They are skipped otherwise, so CI without a database is unaffected. `scripts/live/serve.mts` serves the same API for an external client (the Terraform provider, curl).

## Status page v2 (phase 15)

Pages, audiences, languages, channels, history, embeds, a snapshot that survives the application, and incident drafting from component state. Everything the internet sees still comes from ONE allowlist serializer (`status.public.service.ts`: `buildPublicStatus` for the frozen legacy payload, `buildPublicPage` and `buildPublicArchive` for the page API); the feeds, the calendar, the badge, the widget, the snapshot and the subscriber webhooks are pure renderers over its output and never see an entity.

- **Pages** (`status_pages`). The tenant's original page is the DEFAULT page and needs no row: with none it is the virtual public page it always was (`GET /api/public/status` and `/status` keep their URLs, the disabled-equals-404 rule and their exact payload). A row appears on the first edit. Others live at `/status/p/<slug>` and `GET /api/public/status/pages/<slug>`. A page has an audience, a name, a colour scheme (never a status colour), extra languages, an optional component selection (a PUBLIC page can never show a component that is not public, whatever the selection says), embed origins, an optional host and a snapshot switch. The legacy endpoint answers only while the default page is PUBLIC and on; once it is restricted it answers the common 404 and the page API serves it.
- **Groups and display.** One level of groups (`status_component_groups`, ordered, collapsed or not) and per-component options: show uptime, show the 90-day bar, show regions (drawn: see "Region breakdown" below), show the response-time chart (off by default).
- **Audiences.** `PUBLIC`, `PASSWORD` (bcrypt hash; `POST .../unlock` sets a signed, page-bound, 12-hour HttpOnly cookie that also binds a fingerprint of the current hash, so a new password signs everybody out; 8 wrong guesses per client and 120 per page per 15 minutes then 429, spent identically whether or not the page exists, one bcrypt comparison either way), `AUTHENTICATED` (a signed-in member of THIS tenant, decided by the platform guard at GUEST scope with `observability.status.view`, never by a cookie of ours), `IP` (the client address, first `x-forwarded-for` entry, on a CIDR list; an empty list admits nobody). **Anything not allowed is the same 404 as a page that does not exist, byte for byte**: unknown slug, disabled page, disabled tenant, wrong password, refused audience, other tenant's slug, hostile slug (checked by shape before any read). A check that errors closes the page. Non-public answers are `private, no-store` with `Vary: Cookie`.
- **Hosts.** The free path (`/status`, `/status/p/<slug>` on the tenant's own platform subdomain) needs nothing. A custom host must already be registered AND verified by this tenant in `tenant_domain` (which enforces the plan feature `custom_domain`, the domain cap, the reserved list and global uniqueness) and the plan is checked again when binding; every refusal reads the same and never says who owns a name. In domain mode the proxy serves a bound host's root `/` as that page: it decides with ONE Redis read of `status:host:<host>` (`<tenantId>:<slug>`, mirrored by the page service on every edit and re-asserted by the five-minute heartbeat with a 30-minute life, `status.host.ts`), no database and no observability import, and only when that tenant is the one `tenant_domain` resolved the host to; anything unreadable or malformed serves the tenant's site. **Not done by this code and recorded as dependencies:** the DNS records themselves (the tenant's zone) and the certificate (the reverse proxy through `tenant_domain`'s on-demand TLS gate).
- **Subscribers** (`status_subscribers`): email (unchanged), SMS (E.164, through `notification_sms`), signed webhook (the `webhook` module's address guard at subscribe time and again at every delivery, its v2 signature scheme `sha256=` HMAC over `<timestamp>.<body>`, no redirects, one retry, ten failures in a row switch the endpoint off). Double opt-in on every channel: the confirmation of a webhook goes to the endpoint and carries the signing key (encrypted at rest), so the key reaches whoever controls the endpoint and nobody else; confirmation messages are capped per target (2 minutes) and per tenant per day (200). Subscriptions can be scoped to components, to a (public) page and to a language; anything refused ends in the same 202 as always. Webhook bodies are the page projection of the incident, never the row. Operators see the channel, a masked number and the endpoint HOST only.
- **Feeds, calendar, badge, widget, archive.** `GET .../feed?format=atom|rss[&componentId=]`, `.../calendar` (iCalendar, active and upcoming maintenance), `.../badge[?componentId=]` (SVG, PUBLIC pages only), `.../widget` (script-free HTML, PUBLIC pages only; frameable only by the origins the owner listed, otherwise `frame-ancestors 'none'` and `X-Frame-Options: DENY`; `proxy/csp.ts` leaves exactly this path's framing headers to the route), `.../incidents?before=&limit=` (the full archive, keyset paged). **No tenant-authored script exists anywhere on the page** (locked decision: no `customJs`).
- **History.** Per-component 90-day bars from the daily rollup (two queries for the page), one status per day (`NO_DATA` is not "operational"), incident markers by start day.
- **Language.** The tenant's primary language is the source and the fallback. A page offers the primary language plus the languages its owner turned on; `?lang=` outside that list is ignored. Names and descriptions of components, groups and pages, incident titles and messages and update messages are translated through `status_translations` (per entity, per language, empty clears); any text without a translation is shown in the primary language and the page says so (`language.fallback`). Subscribers pick a language and their mails use the incident's translation when there is one. Right-to-left languages flip the page direction. The page's own words (chrome, status and severity labels, dates, the browser title) follow the served language too: there is no admin shell above `/status`, so the server app-page seeds the client page's `I18nProvider` with the visitor subset of the dictionary (`observability.status.*`, database translations laid over it: `ui/status-messages.ts`), and the title names the page only when it is on and PUBLIC.
- **Resilience (the differentiator).** `status.snapshot.service.ts` writes an HTML and a JSON file per language to `<tenant>/status/snapshots/<slug>[.<lang>]` in the tenant's storage, built ONLY from the serializer, for PUBLIC pages only: on every status change in a process that runs the boot task (debounced), on a five-minute heartbeat (boot task or `POST /api/cron/status-snapshot`), or on demand from the admin screen. An unchanged page is rewritten after four minutes so "last updated" means "last confirmed"; the HTML always prints when it was generated and shows a banner after 15 minutes (a hash-pinned platform script reveals it; the page's own CSP forbids everything else). A page that stops being public has exactly its files deleted. Serving is a second origin that shares no failure domain with the app: [ADR-0010](../../docs/adr/0010-status-page-snapshot-served-from-a-second-origin.md). `storage` gained `putStaticObject` and a `trusted` provider option (server-generated content, folder still registered) because its provider refused HTML and JSON and `uploadServerBuffer` would have written an audit row and a usage increment on every heartbeat. Not verified end to end against a real bucket and CDN (an operator step, see the checklist).
- **Auto-post and auto-resolve** (`status_automations`, one template per component). When a component, driven by its monitors, gets as bad as the template's threshold, an incident is drafted from the template's wording (the closed placeholders of the update templates, replaced as text); it is PRIVATE unless the template carries `autoPublish`, and writing a template with `autoPublish: true` takes `observability.status.publish` on top of `observability.status.manage`, the permission that already guards publishing an incident. A PUBLIC incident that names the component and is already open wins (nothing is drafted); one draft per component at a time (alert-group key `status-auto:<component>`); recovery resolves the draft, with the closing words once when it was published. Operator-set statuses and MAINTENANCE never trigger it.
- **Permissions:** `observability.status.view` (GUEST floor, only lets the audience gate ask the platform guard about membership), `observability.status.read` and `observability.status.manage` (ADMIN), and the existing `observability.status.publish` (ADMIN) for everything that makes a page more visible: making it PUBLIC, switching it on, embedding it, binding a host, auto-publishing.
- **Screens:** `/status/p/<slug>` (public), `/admin/status-pages` (pages with the audience-aware editor, groups and per-component display, translations, subscribers of every channel, auto-post templates, snapshot status and "publish now"). `/admin/status` is unchanged. **kui-react follow-ups** (no matching component exists, so these are plain lists and tables, not one-offs): an inline-edit list, a multi-line text area, a day-bar history chart, a language switcher.

### Slack and Teams subscribers (respond track, migration 067)

### Region breakdown, response-time chart, audience incidents, snapshot chrome and incident translations (respond track)

- **Per-location daily rollups (phase 10.5, D-OBS-12).** A new ADDITIVE table `monitor_check_daily_location` (key `tenantId, monitorId, locationKey, day`; counters `up`, `degraded`, `down` plus the latency aggregates below) is written by the same call
  and in the same transaction as the monitor-level rollup (`StatusUptimeService.bumpDaily`), after the same maintenance-exclusion decision, so the two tables cannot disagree about a sample and a sample that the monitor-level rollup
  skips during maintenance is skipped here too. Both writes are atomic `INSERT ... ON CONFLICT DO UPDATE SET counter = counter + 1` statements, so concurrent writers neither lose nor double an increment (proved against real Postgres,

## Probe locations and runners (phase 10)

A monitor runs from `local` (the in-process probe, the default) and/or from **locations**: public ones published by the ROOT tenant, and private ones a workspace creates for a runner inside its own network.
With two or more, each location debounces its own samples and the monitor is DOWN when `quorum` of them are DOWN (default: a majority of the locations that report); a minority down is DEGRADED and the alert names who saw it.
A location that stops reporting is stale and left out of the count, never counted as down or up.

- **Runner** (`runner/`, image in `infra/docker/probe-runner`): pulls leases, runs the SAME probe code, posts results; no inbound port, no platform secret, its Ed25519 key never leaves its host.
  Every request is signed (method, logical route, time, nonce, body hash); a result is accepted only against a live unconsumed lease of that runner (idempotent on the lease id).
- **Private policy:** a private runner is given only targets its tenant's allow-list names (hostnames) and may reach, besides public addresses, only the declared CIDRs. A public runner never receives a private target nor any secret.
- **Routes:** `/api/probe-locations*`, `/api/probe-runners/[id]`, `/api/monitors/[id]/locations` (admin, `observability.locations.read|manage`), `/api/public/probe/{enrol,lease,results,heartbeat}` (runner credentials).
- **Limits:** `observability.limit.locations_per_monitor`, `observability.limit.private_locations`. Changes to what may be reached are audited with both sides.
- **Lease caps and shedding (control plane).** Besides the runner's own `PROBE_CONCURRENCY`, the control plane bounds how many leases may be OUTSTANDING (handed out, not yet resulted or expired):
  per tenant by the plan limit `observability.limit.runner_leases` (else the deployment default `OBSERVABILITY_PROBE_TENANT_LEASE_CAP`), and platform-wide by `OBSERVABILITY_PROBE_GLOBAL_LEASE_CAP`.
  **Unset or `0` means no cap (the behaviour before caps existed; nothing is counted).** Both env values go through the validated env schema (`.env.example`); the plan key is the usual limit mechanism, with one exception:
  `0` is "no cap", not "not on this plan", because a cap of zero would stop all probing. When a cap is hit, the lease handler hands out the highest-priority due checks first and **sheds** the rest: they stay due, are not lost and are
  leased on a later poll as results or expiry free capacity; no sample is fabricated for them. **Priority** (`probe.caps.ts`): class 0 liveness (heartbeat-adjacent: PING, DNS; a HEARTBEAT monitor is pushed to and never leased)
  > class 1 network checks (HTTP, TCP) > class 2 heavy checks (STEPS, TLS, DOMAIN); inside a class the **shorter interval wins** (more frequent = higher priority), then the check that has waited longest, then the id.
  **Fairness:** priority orders one tenant's checks; the platform's room is shared between tenants max-min fairly (a small tenant is served in full, the rest split what is left, an odd leftover goes to the tenant whose next check
  ranks higher), so a tenant at its own cap or with a huge backlog cannot starve another. The caps are soft under concurrency (two polls reading the count at the same instant can overshoot by one poll's worth).
  Visibility: counter `probe_leases_shed_total{reason=tenant|global, tenantId}`, per-location totals in `GET /api/probe-locations/[id]/runners` (`shed`), `shed` (count) in the lease response, `probe_runner_leases_shed_total` on the
  runner's `/metrics` and a bounded log line (one per location and reason per minute). Migration `064` adds the partial index the count uses.
- **Chaos run (live).** `npm run observability:chaos` starts a real control-plane process over a throw-away Postgres database (and Redis db 14) plus real runner processes built from the production bundle, kills runners, flips the
  target per location, forges and replays requests, crosses the clock-skew bound and exercises the caps; `SECURITY_TEST_LIVE=1 npx vitest run modules/observability/server/tests/probe.chaos.live.security.test.ts` is the same run as an
  opt-in test. About 16 minutes (a silent runner's 3-minute staleness window is waited out for real; `CHAOS_QUICK=1` shortens it). Files: `scripts/probe-chaos*.mts`, `scripts/probe-chaos-runner-shim.cjs`.

## Browser checks (phase 09, D-OBS-8)

A `BROWSER` monitor walks a real page with headless Chromium. It is **expensive and widens the attack surface**, so it is confined by construction:

- **It never runs in the app process.** `runCheck` answers `UNKNOWN` for the type, the in-process sweep and "check now" skip it, and a write refuses a BROWSER monitor whose locations are `local` or empty. Only a probe runner built for it runs it (`infra/docker/probe-runner/Dockerfile.browser`, a separate bundle `probe-runner-browser.mjs`; the plain runner contains none of it, and a test proves that by name and by size).
- **Off by default, twice.** The plan key `observability.limit.type_browser` (0 = not in the plan; undeclared is unlimited by this module's rule) AND the workspace setting `observabilityBrowserChecksEnabled` (default false) must allow it, at write time and again at lease time. `observability.limit.browser_monitors` caps the count.
- **Bounded declarative grammar** (`server/uptime.browser.schema.ts`): `goto` (a literal http(s) URL, no templates or credentials), `click`, `fill` (the only field that may carry `{{secret.NAME}}`), `press`, `waitForSelector`, `waitForText`, `expectText`, `expectVisible`, `expectUrl`. At most 20 steps, first step a `goto`, per-step timeouts, the monitor's `timeoutMs` (5 s to 120 s) as the whole-run budget, an interval floor of 5 minutes whatever the plan says. Assertions: load time, LCP and CLS budgets (DEGRADED by default, DOWN when asked), no uncaught page errors, no failed or 4xx/5xx main-document request.
- **Capabilities.** A runner reports `capabilities: ["browser"]` at enrolment and on every heartbeat (additive; runner version 1.1.0; a 1.0.0 runner is still fully supported and never reports one). The lease service hands a BROWSER check only to a runner that reported it, at a private location or a public location the ROOT tenant enabled for browsers (`browserEnabled`), at most 4 browser leases per poll and 2 per tenant, with a lease that allows for the browser launch. A location with the flag refuses to enrol a runner that does not report the capability. The runner reports the capability only while a real launch works and withdraws it after three failed launches in a row.
- **SSRF and isolation** (`runner/browser/`): Chromium is launched per check behind a forward proxy on 127.0.0.1 (per-check credential) that applies the same connection guard as every probe (`public_or_listed`, every address judged, the connection pinned to the validated address, CONNECT and WebSocket included, redirects judged hop by hop because each hop is a new request), with `--host-resolver-rules` so it resolves nothing itself, loopback proxied too, WebRTC UDP and QUIC off, service workers blocked, downloads refused, popups closed, `file:`/`chrome:`/`javascript:` navigations aborted, a fresh context and profile per check, a minimal environment, and a watchdog that measures the whole process tree from `/proc` and kills it on memory, CPU time, process count, bytes through the proxy or the wall-clock budget.
- **Results.** Per-step timings and web-vitals (bounded JSON, 8,000 characters) are stored with the sample in `monitor_check_details`; the sample list route adds them as `browser` and `hasScreenshot`. A failed run also carries one JPEG (at most 300 KB after the runner downscaled it; typed secrets and password fields are painted over). **Where the screenshot lives and why** is recorded in `uptime.check-detail.service.ts`: in the tenant's own database row, not the `storage` module, so retention is one statement on the raw-check cutoff, isolation is RLS plus the route permission, it works without `storage`, and the cost is bounded (300 KB, failures only, newest 30 per monitor keep their bytes). Read it with `GET /api/monitors/{id}/checks/{checkId}/screenshot`, permission `observability.screenshots.read` (ADMIN), `image/jpeg`, `nosniff`, `no-store`.
- **Operations:** see `infra/docker/probe-runner/README.md` (browser section) for the image, the compose file, the seccomp note and the limits. Migration `090_browser_checks.sql`.

## MCP server, AI investigator and LLM observability (phase 20)

Spec: `docs/phases/09-observability/20-mcp-and-ai.md`. Everything AI is **off per tenant until an admin turns it on** (`/admin/observability/ai`, permission `observability.ai.manage`); with it off, nothing is read, built or sent.

### MCP server (`/api/mcp/observability`)

A hand-written MCP surface: JSON-RPC 2.0 over streamable HTTP, stateless, POST only (GET and DELETE are 405), no batching. Methods: `initialize`, `ping`, `tools/list`, `tools/call`; notifications are accepted. Protocol revisions answered: 2025-06-18, 2025-03-26, 2024-11-05. **It is driven by the official `@modelcontextprotocol/sdk` client** (a devDependency, version 1.32.1 when this was written): `server/tests/mcp.sdk-client.suite.ts` runs the same conversation against the handler with in-memory dependencies (always) and, with `OBS_LIVE=1`, against the real tenant dispatcher over a real Postgres, Redis and api keys (see "Live lane" below).

| | |
|---|---|
| Auth | `Authorization: Bearer <api key>` of the tenant, holding exactly `observability:mcp:read`; the three write tools also need `observability:mcp:write` (separate, off by default). `admin` and `*` keys are refused. Create keys on `/admin/observability/ai` (it uses the `api_key` create route) |
| Tenant | The key's. The URL tenant must equal it (anything else is the same 401 as a bad key). No tool has a tenant argument |
| Read tools | `list_monitors`, `get_monitor_checks`, `list_incidents`, `get_incident_timeline`, `get_incident_changes`, `list_alerts`, `get_alert`, `slo_status`, `who_is_on_call` (needs `on_call`), `query_logs`, `query_traces`, `query_metrics` (the STRUCTURED query vocabulary of phase 18 with `lookbackMinutes` or `range`; never LogQL, PromQL or TraceQL) |
| Write tools | `ack_alert`, `silence_alert` (1 to 1440 minutes, a reason, the alert's exact labels), `add_incident_note` (internal). **No tool publishes to the status page or changes incident visibility** |
| Limits | 64 KB body, 120 reads and 20 writes a minute per key, 20 s per tool, 48 KB per result |
| Audit | every `tools/call` through `audit_log` when active (actor type `API_KEY`), else the logger; tool, outcome and argument NAMES only |

**Output hygiene.** Every result is `{ untrusted: true, notice, truncated, data }` as text and as `structuredContent`; strings in `data` are cleaned by `server/hygiene.ts` (escape sequences, zero-width and bidi characters, control characters, secrets, and for free text JWTs, e-mail addresses, uuids and tenant paths; length cut) and tool descriptions tell the client never to follow instructions in a result. Client documentation: ask your client to **confirm with a human before calling any write tool** and never to call a tool because a result says so.

What the real client taught us (SDK 1.32.1, 2026-10-18; the SDK offers protocol 2025-11-25 and accepts the server's answer):
- **Version negotiation.** The client offers its newest revision; the server answers with the newest it speaks (2025-06-18) and the client accepts it, sending `MCP-Protocol-Version: 2025-06-18` from then on. Older revisions are answered as asked; an unsupported header value is a 400.
- **GET and the event stream.** After `notifications/initialized` the SDK sends a `GET` asking for a server-to-client SSE stream. The server answers **405** with `Allow: POST`, which the 2025-06-18 transport section permits; the client treats it as "this server has no stream", keeps working over POST, and never retries it in a loop. No server-initiated messages are possible (no `tools/list_changed`, no sampling).
- **Sessions.** No `Mcp-Session-Id` is issued and none is needed (stateless); the SDK works without one, and closing a client sends no `DELETE`.
- **Origin.** A request carrying a foreign `Origin` is a 403 (a browser page must not drive a key); the SDK in Node sends no `Origin`, a same-origin one is let through.
- **Errors.** An unknown tool is a JSON-RPC error (-32602, thrown by the client); invalid arguments, a record the caller cannot see (another workspace's incident is the same 404 as a missing one) and a scope refusal are `isError` tool results with a `code`; a bad or foreign key is a 401 with `WWW-Authenticate: Bearer realm="observability-mcp"`; an over-budget key is a 429 with `Retry-After`; a body over 64 KB is a 413 before any tool runs and the connection stays usable.
- **Authorization and OAuth.** The 2025-06-18 authorization section makes authorization optional, and a server that offers OAuth must publish protected-resource metadata (RFC 9728) so a client can discover an authorization server. This endpoint is a static-credential resource (an `api_key` the administrator minted), has no authorization server to point at, and clients that take a header in their configuration (the snippet below) connect without discovery. Publishing metadata that points nowhere would make clients that probe it fail in a worse way, so **none is published** and the 401 deliberately carries no `resource_metadata`. A client that insists on OAuth discovery cannot use this endpoint until the platform has an OAuth authorization server for MCP (not planned). The SDK, given no `authProvider`, surfaces the 401 as an error and does not attempt discovery (tested).
- **Found live, fixed:** the write tool `add_incident_note` failed in production (the `comments` module needs an UPPER_SNAKE subject type and an author; mocked tests had pinned the broken call). Incident notes from the console had the same defect.

### AI features (all advisory, all cited, nothing applied)

| Feature | Route | What it does |
|---|---|---|

Gate order (`ai.gate.ts`): tenant switch, a provider on the tenant's **allow-list** (the first one is used, empty means none; the list is the residency control), the daily cap (`dailyCap`, default 20, all features together, failed runs count, 0 means none; rows in `incident_ai_notes`), then `ai`'s plan and token quota. The call is `AIService.chat` for the tenant, so it runs on the tenant's own provider configuration and appears in `ai`'s usage log. The daily cap follows the `ai_agent` pattern (a kill switch, a cap, an entitlement) but is this module's own setting; `ai_agent` is not a dependency.

Data: tenant tables `incident_ai_notes` (migration `030_ai_runs.sql`) and `incident_embeddings` (migration `070_incident_embeddings.sql`); the switches are one JSON tenant setting `observabilityAiSettings`, changed with `PUT /api/observability/ai/settings`, a strict patch: an omitted field is kept and `model: null` clears the model override (back to the provider's default).

**Similar incidents** (work order 2). Every incident is indexed into the `search` module under entity type `incident` when it opens, is edited, resolves and when its post-mortem is published (`server/incident.search.ts`: title, reason, severity, monitor name, the titles and labels of its alerts, the post-mortem root cause; secrets and control characters removed; metadata carries status, severity, start and duration). A backfill (`backfillIncidentIndex`, paged, idempotent) covers older incidents. The lookup is an OR query of the incident's distinctive words (`similarityQuery`: letters and digits only, so no operator reaches `websearch_to_tsquery`), restricted to RESOLVED incidents and never the incident itself, merged after the group and monitor matches. Embedding similarity is opt-in per tenant (`similarByEmbedding`, off by default, needs an `ai` provider with embeddings; `embeddingModel` optional): the text is embedded through `AIService.embed` on the tenant's own allow-listed provider, L2-normalised and stored as `real[]`, compared with cosine over the tenant's most recent 300 vectors of the SAME model, with a per-tenant daily cap of 200 embedding calls and an unchanged text costing no second call. pgvector 0.6.0 is installable on the development Postgres; the implementation does not require it (the candidate set is small and no extension is needed to deploy), and a live test cross-checks the service's cosine against pgvector's `<=>` operator. **Not run against a real embedding provider** (no key in this environment).

**Automatic runs.** The run on incident open is a DELAYED job: `autoRunDelayMinutes` (tenant setting, default 2, 0 = at once, at most 60) because the evidence is thinnest when an incident opens. A BullMQ job with the deterministic id `ai-auto__<tenant>__<incident>__<phase>` (scheduling twice schedules once) runs `runAutoInvestigation`, which re-reads everything at run time and applies the caps: at most one automatic run per incident per phase (trigger `AUTO` for open, `RESOLVE` for the optional second run when the incident resolves, `onIncidentResolve`, default off), a Redis claim so two nodes cannot both start it, the tenant's daily cap inside the gate, and an incident that resolved during the delay is left to the resolve run when that is on. A once-a-minute sweep (`ai.auto.job.ts`, and `POST /api/cron/ai-auto` for serverless) runs what is due and has not run (at most 5 per tenant per sweep): it is also the safety net for a lost job or a changed delay.

**Conversation timelines and cost** (the incident AI tab and the LLM page draw them with the vendored kui `ConversationTimeline`). `GET /api/incidents/{id}/ai/timeline` (`observability.ai.use`): per run the evidence built (counts by kind, unavailable sources), the model call (provider, model, tokens, cost), the citation filter (claims kept and dropped) and the outcome and feedback, with MCP tool calls on the incident (audit rows) interleaved by time. Cost comes from the `ai` usage log: a run is matched to the row that billed it by tenant, provider, model, EXACT token counts and a short window, so it is what was billed; unmatched means `costUsd: null`. `GET /api/telemetry/genai/conversations/{conversationId}?lookbackMinutes=` (`observability.telemetry.read`): the steps of a tenant application's conversation from OTLP `gen_ai.*` spans (model calls, embeddings, agent invocations, tool executions, retrievals) with tokens, errors and an ESTIMATED cost from the price table `ai` uses for its own log (`costEstimated: true`; null for an unpriced model).

**Evaluation.** `npm run eval:investigator -- --live` runs the same six incidents against a REAL provider through the `ai` module with the tenant's own key and scores citation validity (share of raw claims citing only existing evidence), drop rate, groundedness (share of the salient tokens of every kept claim, numbers, versions, identifiers and names, found in the evidence it cites; a lexical heuristic), expected-finding coverage and cost (tokens from the reply, dollars from the usage price table), against thresholds (0.9, 0.2, 0.7; flags `--min-validity`, `--max-drop`, `--min-grounded`, `--max-calls`, `--out`). Without a provider key it runs NOTHING and exits 3; it never falls back to the fake model. `--key-from-env` stores `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` or `GOOGLE_AI_API_KEY`/`GEMINI_API_KEY` in the evaluation tenant's settings for the run. The scoring and runner are tested with scripted models (`ai.eval.live.test.ts`). **No live run has happened: no provider key exists in this environment** (D-OBS-16). `npm run eval:investigator` (no flag) runs a golden set (`server/ai/eval/golden/*.json`, six incidents) through the investigator with a fake model, deterministic and offline: expected evidence kinds, expected cited findings, every claim resolves, and attacks fail closed (hallucinated ids, uncited claims, garbage and wrong-shape replies, an obeyed prompt injection, secrets in the evidence). It is also a vitest suite (`ai.eval.test.ts`). Run it before changing the prompt (`ai.prompt.ts`, versioned), the schema or the citation filter.

### Scaling view (process supervisors)

`docs/phases/14-docker/07-process-scaling.md` task 6 (owner decision D4). A kind with `PROC_<KIND>_ENABLED=true` runs as a
`process_host` **supervisor** that forks and scales child processes. `server/process.scaling.service.ts` reads it only
through `process_host`'s readers (`listKinds`, `readProcessNodes`, and `readSupervisorState` / `readSupervisorEvents` /
`readSupervisorSignal` from `@kuraykaraaslan-labs/process_host/server/supervisor/publisher`); observability depends on
process_host, never the reverse.

- **Finding supervisors.** Registry nodes with `info.role = 'supervisor'`, then their `proc:sup:<kind>:<nodeId>` state.
  A state that is missing or older than its 15 s TTL is **stale** and left out (counted in `stale`), so a stopped group
  never shows as running. Redis unreadable → `redisError`, shown as "unknown", never as "scaling is off".
- **Per supervisor** (`listSupervisors()`): kind, host, pid, status (`steady | scaling | cooling | frozen`), budget
  (cpu, memory, max, allocation), policy (min, max, upAt/downAt with their holds, cooldowns, drain grace), the current
  signal, `frozen`, the last 50 decisions (`proc:sup:events:*`, newest first) and the **last hour of the smoothed signal**
  (`proc:sup:signal:<kind>:<nodeId>`, a bounded list the supervisor writes every 5 s — 720 points, TTL 1 h — added to
  process_host for this view because the state only holds the current value).
- **Children** carry index, pid, uptime, state, health, restarts and, for `automation-worker`, the **partitions** each
  child holds: joined from the child's own registry row (`info.role = 'child'`, `info.supervisor`, `info.childIndex`)
  where the automation host's info provider reports `info.automation.partitions`. No extra field in the supervisor state.
- **API.** `GET /api/processes/scaling` (`server/processes-scaling.route.ts`): ROOT tenant only (404 elsewhere, before
  any check), the processes page's permission `observability.processes.read`. Read-only: a policy changes through env.
- **Screen.** `/admin/system/processes` has two tabs: *Processes* (the registry, above) and *Scaling*
  (`ui/processes-scaling.component.tsx`, loaded when the tab opens, refreshes every 5 s while the browser tab is visible).
  Supervisors are grouped by machine, one card per kind (`ui/processes-scaling-card.component.tsx`): status badge,
  budget, policy, the signal line against `upAt`/`downAt` for the last hour (kui `LineChart`, time axis,
  `ui/processes-scaling-chart.component.tsx`), the children table, the decision log (time, action, from → to, reason,
  signal), a crash-loop banner on the card and one on the page. No supervisor → "Scaling is off for every kind".
- **CPU** (optional fields since 07 task 5, so a card from an older supervisor shows none of this): a *CPU* column in the
  children table (`PublishedChild.cpu`, percent of one core), the policy fact *Down also needs CPU* (`policy.downCpuBelow`)
  and, under the signal line, the group CPU (`PublishedSignal.cpu`, the 30 s average of the children) against the scale-down
  CPU condition (`signal.downCpuBelow`, the `cpu_down` edge of `process_scale_threshold`): met, too busy to shrink, or no
  reading (no CPU reading means no signal-driven scale-down). Without a condition the line shows the CPU alone.
- **Relayed supervisors:** the credential-less supervisors (`script-host`, `plugin-host`; 07 task 7) hold no Redis, so the
  worker on their node relays their `GET /supervisor` (ports 4015 and 4501) into the same `proc:sup:*` keys and a
  `proc:nodes:<kind>` supervisor row (`info.relayedBy: 'worker'`; process_host `supervisor.relay.ts`). The reader needs no
  special case: they are listed like every other supervisor, and drop out within 15 s when the relay stops reaching them.
- **Crash-loop alert.** `evaluateCrashLoops()` runs on the same minutely `observability-process-check` tick (and its
  cron twin) through `server/process.checks.ts`: a kind with a frozen supervisor opens one auto, private ROOT-tenant
  incident (`reason = "source:process-crash-loop kind:<kind>"`, MAJOR), deduplicated by that reason while open, resolved
  when no live supervisor of the kind is frozen any more: all report unfrozen, or none is left (state gone or stale: the
  group was stopped, redeployed or turned off; a kind that should run is the expected-process check's business). An
  unreadable Redis changes nothing. Prometheus carries the same condition as the `ProcessCrashLoop` alert (`max by (kind) (process_crash_loop) == 1`
  for 1 m) in `server/alert-rules.ts` → `infra/prometheus/alerts.yml`.

## Custom metrics, spans, SLIs and alerts

**Custom metrics** (`server/metrics.custom.ts`). `const orders = ObservabilityService.counter({ name: 'orders_created_total', help: '…', labelNames: ['channel'] })` at module scope, then `orders.inc({ channel: 'web' })` anywhere. The handle is a no-op before init, with `METRICS_ENABLED` off or `prom-client` missing, so callers never guard. Names are `snake_case` and may not shadow a built-in or an `app_*` default; `le` / `quantile` labels are refused; a `tenantId` label goes through the same cardinality bound as the built-ins; and each metric accepts at most 1000 distinct label sets (the overflow is dropped and warned once — a runaway label must not take the scrape down). Redefining a metric with the same shape is idempotent; with a different shape it throws at definition time.

**Noise and sampling** (`server/sentry.filters.ts`). `beforeSend` drops Next control-flow throws plus `SENTRY_IGNORE_ERRORS`. `tracesSampler` (which replaces the flat `tracesSampleRate`, keeping the same base rate) returns 0 for probe routes, follows an upstream sampling decision so distributed traces stay whole, then applies `SENTRY_TRACES_TENANT_RATES` (tenant id read best-effort from the `/api/tenant/<id>/…`, `/tenant/<id>/…` or `/t/<id>/…` path), then the base rate (`ObservabilityService.setTracesSampleRate(rate | null)` overrides the base rate at runtime for the current process).

**Spans** (`server/tracing.ts`). `ObservabilityService.withSpan('billing.invoice.render', (span) => { span.setAttribute('lines', n); return render() }, { op: 'task' })`. Sync and async callbacks both work; the result and any thrown error pass through untouched. With OpenTelemetry the span records the exception and ends on every path.

**SLIs.** `GET /api/slo[?route=…]` (ROOT tenant, `observability.slo.read`) returns this process's p50 / p95 / p99, 5xx ratio and request count since boot, computed from the request histogram with Prometheus' own interpolation (`server/slo.ts`). It is per-instance and since-boot by construction; for windows and multi-instance fleets use the recording rules below.

**Alert rules.** Thresholds live in `server/alert-rules.ts`; `infra/prometheus/alerts.yml` is generated from them (`npm run gen:alert-rules`, `npm run check:alert-rules`; a unit test fails on drift). Rules: error ratio, p99 latency, monitor DOWN / DEGRADED, per-plugin failure ratio, event-loop lag, metrics target missing, plus the `http:request_duration_seconds:p95_5m` / `p99_5m` and `http:requests:error_ratio_5m` recording rules. Point Prometheus `rule_files` at the generated file.

**Provider probe targets.** A module that depends on an external endpoint (a national-id or e-signature provider, say) contributes to the `observability:probe-target` extension point instead of building a health checker: its default export `{ listTargets(tenantId) }` returns the targets that exist for the tenant, and the minutely sweep reconciles them into `Monitor` rows (`sourceKey = <moduleId>:<key>`). The provider owns a managed monitor's identity, target and active flag — created on first sight, updated on change, **deactivated (never deleted)** when the provider stops reporting it. A provider that throws leaves its monitors alone, since failing to enumerate is not evidence a target is gone; an operator opts a target out by deleting its monitor (the soft-deleted row keeps the key, so it is not resurrected). Malformed specs are skipped and counted. Contributors today: `auth_national_id` (every enabled IdP's SSO/auth endpoint, ROOT tenant only — the ACS map is platform-level) and `e_signature` (aggregator / EU trusted list / default TSA on ROOT; each tenant's own Smart-ID and BankID endpoints). Both emit TCP targets, because these endpoints answer a bare HTTP GET with 3xx/4xx, which an HTTP check would call DOWN. A contributor that is merely *useful with* observability (not dependent on it) lists the pair in `CONTRIBUTION_ONLY_EDGES` (`scripts/registry/imports.accepted.mjs`) instead of adding it to `requires`. Everything else — probe, debounce, incident, status component mapping — is the ordinary monitor path, so provider health has exactly one source.
